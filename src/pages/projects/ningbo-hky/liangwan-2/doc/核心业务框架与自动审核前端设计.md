# EcoCenter 核心业务框架与自动审核前端设计

本文档给新接手项目的开发者和前端开发者使用。它不要求先了解所有代码，而是先解释“数据从哪里来、经过了什么、最后保存在哪里”，再说明自动审核和页面应如何配合。

## 1. 这个服务在做什么

EcoCenter 是一个“接收监测设备数据、检查数据、保存数据、提供查询”的服务。

设备可以通过两种方式进入系统：

1. 设备或其它系统调用 HTTP 的 HJ212 接口。
2. 设备连接 TCP 网关，网关收到 HJ212 文本后放入进程内通道，再交给同一个应用服务处理。

两种入口最后都会走同一条业务流程，因此不会出现“HTTP 收到的数据审核方式不同、TCP 收到的数据审核方式不同”的问题。

```text
设备 / HTTP 调用
        │
        ▼
解析 HJ212 报文（必要时先重组分包）
        │
        ├── 保存每个物理报文原文
        │
        ▼
按参数拆成数据点 → 自动审核 → 保存数据点和审核结果
        │
        ├── 审核失败时调用通知扩展点
        │
        ▼
前端通过表格、曲线、轨迹、获取率等接口读取数据
```

## 3. 一条数据如何入库

以 `CN=2011` 的实时数据为例，处理顺序固定如下：

1. 读取报文的 `MN`，找到站点当前配置；未知站点不写数据点。
2. 完整解析 HJ212。若 `Flag` 的 bit1 为 `1`，先按 `MN + QN + CN + PNUM/PNO` 收齐分包；每个物理分包原文都会留存。
3. 保存原始报文到 `ingestion_message`。这个表只负责留档和排查，不再维护复杂状态机。
4. `CN=2011` 处理器把 CP 中的参数拆为数据点草稿：参数编码、业务时间、原始值、有效值、数值、全部指标。
5. 自动审核协调器为每个数据点找出本站点绑定的规则，执行规则并生成审核草稿。
6. 在一个短事务中写入 `measurement_point` 和一对一的 `measurement_audit`。若同一业务唯一键已经存在，按内容判断为重复或冲突，不覆盖旧记录。
7. 事务提交后，若有规则结论为 `Failed`，调用 `IAutoReviewNotificationSender`。通知发送失败只记日志，不回滚已保存的数据。

这样做的好处是流程直：原文留档、数据审核、数据点保存三件事明确分开；通知属于后续动作，不会因为短信或第三方服务故障丢失采集数据。

## 4. 自动审核的基本概念

一条“规则定义”描述规则是什么、默认怎么判断、作用于哪个参数。一个“规则绑定”表示哪个站点要使用它，以及该站点是否覆盖默认值。

```text
参数定义（例如：水温 060）
        │
        └── 规则定义（例如：水温范围 0~40℃）
                    │
                    ├── 站点 A 绑定：沿用默认 0~40℃
                    └── 站点 B 绑定：覆盖为 2~35℃
```

规则执行后有三种单条结果：

- `Passed`：规则通过。
- `Failed`：规则明确不通过，数据点整体自动审核状态为 `Failed`。
- `Error`：规则无法得出可靠结论，例如缺值、引用的同帧参数不存在或配置错误；没有其它失败规则时，整体为 `Error`。

一个数据点没有绑定规则时，整体状态是 `NoRule`，不是错误，也不是 `Passed`。

### 4.1 三种普通参数审核规则

前端普通参数审核页应提供以下三种规则模板。页面不建议让用户直接编辑 JSON；应使用表单，再由前端生成接口需要的 JSON。

| 模板名称 | `implementationKey`    | 用途                                                         |
| -------- | ---------------------- | ------------------------------------------------------------ |
| 数值范围 | `Range`                | 判断数值是否在允许的上下限内。最常用，例如水温、pH、溶解氧。 |
| 条件比较 | `Comparison`           | 将当前值与固定值或同一报文中的另一个参数比较。               |
| 连续同值 | `ConsecutiveSameValue` | 连续 N 次上报完全相同，通常用于发现传感器卡死。              |

所有模板还有一个共同选项“值缺失时怎么处理”：

| 页面显示       | JSON 值 | 含义                               |
| -------------- | ------- | ---------------------------------- |
| 视为通过       | `Pass`  | 数据缺失不阻断本条规则。           |
| 视为失败       | `Fail`  | 数据缺失直接标记为审核失败。       |
| 标记为规则错误 | `Error` | 默认建议；提示需要检查数据或配置。 |

#### A. 数值范围规则 UI

建议表单字段：

- 目标参数：只读显示当前参数，例如“水温（060）”。
- 审核指标：下拉框。默认“有效主值”；若报文有多个指标，可选 `Rtd`、`Flag` 等后缀。
- 最小值、最大值：允许只填一边。
- 是否包含最小值、是否包含最大值：两个开关，默认都开启。
- 值缺失策略。
- 名称、说明：用于后台列表和审核人员理解规则。

前端生成的默认配置示例：

```json
{
  "metric": "Rtd",
  "minimum": 0,
  "maximum": 40,
  "includeMinimum": true,
  "includeMaximum": true,
  "missingValuePolicy": "Error"
}
```

前端校验：至少填写一个边界；两个边界都填写时最小值不能大于最大值。

#### B. 条件比较规则 UI

适用于“当前值必须小于/大于某个值”或“同一帧两个参数必须满足关系”。

建议表单字段：

- 左侧指标：默认“有效主值”，也可选择当前参数中的某个指标后缀。
- 运算符：`>`、`>=`、`<`、`<=`、`=`、`!=`。
- 右侧来源：单选“固定值”或“同一报文参数”。
- 固定值模式：显示一个输入框。
- 同一报文参数模式：显示参数编码下拉框；可选目标参数的指标后缀。
- 值缺失策略。

固定值配置示例：

```json
{
  "leftMetric": "Rtd",
  "operator": "LessThanOrEqual",
  "right": { "source": "Constant", "value": 40 },
  "missingValuePolicy": "Error"
}
```

同帧参数配置示例：

```json
{
  "leftMetric": "Rtd",
  "operator": "GreaterThan",
  "right": {
    "source": "FrameParameter",
    "parameterCode": "061",
    "metric": "Rtd"
  },
  "missingValuePolicy": "Error"
}
```

同帧参数必须确实由同一类 HJ212 报文一起上传；若设备分开上传，系统不会跨时间去找另一个参数，规则会得到 `Error` 或按缺失策略处理。

#### C. 连续同值规则 UI

建议表单字段：

- 审核指标：默认“有效主值”，也可选择指标后缀。
- 连续次数：整数，范围 2 到 100。
- 值缺失策略。

示例：

```json
{
  "count": 3,
  "metric": "Rtd",
  "missingValuePolicy": "Error"
}
```

含义是“当前值加上此前连续的两个有效历史点，三个值完全相同则失败”。数值 `1`、`1.0`、`1.00` 会视为相同；非数值文本按原文比较。历史不足 N 条时规则通过并记录 `InsufficientSamples`，不会把新设备刚开始上报误判为故障。

### 4.2 圆形围栏是定位专用扩展

程序还内置 `CircularGeofence`。它不是普通数值参数的三种规则之一，应该只在经纬度参数管理页展示。

页面填写经度参数编码、纬度参数编码、半径（米），圆心可以使用站点档案坐标，也可以手动填写。它检查同一帧坐标是否位于圆内。若前端暂时没有定位功能，可先不展示该模板，不影响前三种普通规则。

## 5. 前端创建和绑定规则的完整流程

### 5.1 推荐页面结构

1. **参数列表页**：显示参数定义、站点绑定和所属参数组；每行有“配置审核规则”。
2. **规则定义页**：选择模板、填写默认值、保存为可复用规则定义。
3. **站点规则页**：选择站点和已有规则，决定是否覆盖默认值、设置优先级。
4. **审核数据表格页**：使用 `/measurements/query` 显示点 ID、自动审核状态、人工审核状态；点击单元格可展开每条规则的结果。

### 5.2 保存规则定义

调用：`POST /api/v1/review-rules`。

前端应把模板固定为上述 `implementationKey`，不要让普通用户手写；`code` 建议由“参数编码 + 模板名”生成，例如 `060-range`，但保存前允许修改。

请求中需要的两个 JSON：

- `defaultConfigJson`：表单当前填写的默认值。
- `configSchemaJson`：字段说明和格式约束。对于内置三个模板，前端可内置固定 Schema，不要求用户编辑。

范围规则最小 Schema 示例：

```json
{
  "type": "object",
  "properties": {
    "metric": { "type": "string" },
    "minimum": { "type": "number" },
    "maximum": { "type": "number" },
    "includeMinimum": { "type": "boolean" },
    "includeMaximum": { "type": "boolean" },
    "missingValuePolicy": { "type": "string", "enum": ["Pass", "Fail", "Error"] }
  },
  "required": ["includeMinimum", "includeMaximum", "missingValuePolicy"]
}
```

比较和连续同值规则的 Schema 也应由前端模板固定生成；后端会再次校验，不能只依赖前端。

建议把“新建规则”做成一个三步小向导，而不是一张很长的表单：

1. 先选规则类型，页面立刻只显示该类型需要的字段。
2. 填写阈值或比较对象时，在表单下方同步显示一句人能读懂的话，例如“水温 Rtd 必须小于等于 40”。
3. 点击保存前在浏览器完成范围、必填项和连续次数校验；保存失败时直接把接口返回的字段路径和提示显示在相应输入框下。

不要把 `defaultConfigJson` 文本框作为普通用户的主要入口。可以在“高级查看”里只读展示最终 JSON，方便实施人员核对，但编辑仍应回到表单完成。

### 5.3 绑定到站点

调用：`POST /api/v1/review-rule-bindings`。

```json
{
  "ruleDefinitionId": "301",
  "stationId": "1",
  "configOverrideJson": "{\"maximum\":35}",
  "priority": 10
}
```

- 不覆盖默认值时传 `{}`。
- 覆盖 JSON 只放变更字段，例如站点 B 的最大水温是 35。
- `priority` 数字越小越先执行；所有规则仍会执行，优先级主要用于稳定展示和排查顺序，不是“前一条失败就停止”。

前端保存后应重新读取该站点的绑定列表，并把“默认配置”和“本站覆盖”分两块显示。覆盖为空时显示“使用默认值”，不要在页面上复制一整份默认 JSON；这样用户一眼能看出修改规则定义会影响哪些站点、修改站点覆盖又只会影响哪个站点。

### 5.4 审核表格中的状态展示

原始粒度调用 `/measurements/query`。建议单元格颜色：

| 自动状态 | 建议显示                                                            |
| -------- | ------------------------------------------------------------------- |
| `Passed` | 绿色或正常。                                                        |
| `NoRule` | 灰色，提示“未配置自动审核”。                                        |
| `Failed` | 红色，可点击查看 `autoReviewResultsJson` 中失败规则、阈值和实际值。 |
| `Error`  | 橙色，提示“规则无法判断”，优先检查缺失值策略、同帧参数和配置。      |

只有原始粒度单元格有 `pointId`，可调用人工审核或有效值修正接口。时、日、月均值是计算结果，不应直接人工审核。

点击失败或错误单元格时，建议按下面顺序展示详情：先显示当前值和总状态，再列出每条规则的名称、通过/失败/错误、说明，最后用键值表显示 `facts`。不要要求前端根据 `resultCode` 自己重新计算结论，后端保存的结果就是当时的审核事实。

## 6. 查询接口怎样分工

| 接口                                     | 用途                                           | 是否返回审核状态                         |
| ---------------------------------------- | ---------------------------------------------- | ---------------------------------------- |
| `GET /stations/{mn}/measurements/latest` | 首页或站点详情的最新值。                       | 返回最新点的摘要。                       |
| `POST /measurements/query`               | 审核表格、追溯单点、人工审核入口。             | 返回。                                   |
| `POST /measurements/series`              | 历史曲线、经纬度轨迹。                         | 不返回，行数组只含时间和值。             |
| `GET /data-rates`                        | 单参数或一个参数组中每个参数的获取率、有效率。 | 只按审核状态计算有效率，不返回逐点明细。 |

`query` 和 `series` 都要求一次选择的参数来自同一个站点参数组、同一种类、相同上报周期。这样多列在同一行的时间才能对齐，不会把 15 分钟数据和 1 小时数据放到错误的同一行。

## 7. 常见排查方法

1. **设备报文已收到但没有数据点**：先查 `ingestion_message` 原文；再看 HJ212 响应或日志中的 `UnsupportedCommand`、`MissingDataTime` 等错误码。
2. **自动审核为 Error**：在审核表格展开规则结果，优先看 `resultCode`、`message`、`facts`；通常是缺失指标、比较参数未同帧上报或规则配置不完整。
3. **连续同值没有触发**：确认同一参数的业务时间递增、规则的 `count` 足够小，并确认实际有效值没有变化。
4. **曲线没有数据**：检查选择的是参数定义 ID，不是协议文本编码；检查参数是否数值类型、时间范围和参数绑定。
5. **轨迹缺点**：经纬度必须同一参数组、同周期；某行经纬度任一为空时前端应跳过该点，不应补造坐标。

## 8. 后续增加新规则时

新增规则不需要改入库主流程。只需：

1. 在 `Domain/Reviews/Rules` 实现 `IAutoReviewRule`。
2. 给出唯一 `ImplementationKey`，并在 `Application/DependencyInjection.cs` 注册。
3. 如有特殊配置边界，在 `RuleConfigurationValidator.ValidateBuiltIn` 添加校验。
4. 在前端规则模板列表增加一个表单、默认 JSON、Schema JSON 和说明。
5. 增加单元测试，至少覆盖通过、失败、缺失值和边界值。

这样新规则只增加自己的判断，不会把接收、入库、查询等稳定流程改复杂。
